# CLAUDE.md

## What this repo is

Live-demo material for a 45-minute session at XE One Day: **what's new in C# 15 and EF Core 11**, shown
side by side with the previous versions (C# 14 / .NET 10 SDK and EF Core 10). The audience sees the same
snippet run on two SDKs in two terminals: it fails or behaves differently on .NET 10, works on .NET 11.


## STATUS: executed on SDK 10.0.401 and 11.0.100-rc.3

Scenarios 01 to 17 were run on both SDKs (EF Core 10.0.14 and 11.0.0-rc.3). Findings worth knowing:

- Dictionary expressions (`["a": 1]`) do not compile on rc.3, only `with(...)` does.
- `HasVectorIndex(b => b.Embedding, "cosine")` as in the docs fails on rc.3: the 2nd argument is the index name. Use `.HasVectorIndex(b => b.Embedding).HasMetric("cosine")`.
- A table with a vector index is read-only (SQL Server 2025 preview), and `CREATE VECTOR INDEX` needs `PREVIEW_FEATURES = ON` per database.
- SQL Server 2025 CU10 rejects `VectorSearch(...)` SQL generated by EF 11 rc.3 ("Incorrect syntax near 'TOP_N'"), so scenario 16 only prints it.
- `--context "*"` works on `dotnet ef database update`, not on `migrations add` or `migrations list`.
- Not run, taken from Microsoft docs: split query `DbQueryConcurrencyException`, SqlClient 7 / Entra ID, SQL Server compatibility level 160, TOP(1) for MaxBy on SQL Server.

Scenarios 16 and 17 need a SQL Server 2025 container with full-text installed (`xe-sql2025` on port 14335, image
`mcr.microsoft.com/mssql/server:2025-latest`, then `apt-get install mssql-server-fts` as root from the Microsoft mssql-server-2025
repo and restart) and Ollama with `qwen3-embedding:0.6b` (`localhost:11434`). Override with XE_SQL and XE_OLLAMA.

## Layout

```
net10/                 global.json (pins SDK 10.0.x) + Directory.Packages.props (EF Core 10)
net11/                 global.json (latest installed SDK, prerelease allowed) + Directory.Packages.props (EF Core 11)
scenarios/csharp/      NN-name.old.cs / NN-name.new.cs   (language features)
scenarios/ef/          NN-name.old.cs / NN-name.new.cs   (EF Core features)
shared/                code pulled into scenarios with #:include ../../shared/X.cs (ZooDb.cs: union model + seed, BlogDb.cs: Blog/Post + seed)
run.ps1                runs one scenario on net10, net11 or both
warmup.ps1             runs everything once, output discarded (warm NuGet + build caches)
```

`net10/work/` and `net11/work/` are generated by `run.ps1` (git-ignored). Never edit files in there.

## How it works

- Scenarios are **file-based apps** (`dotnet run file.cs`, `#:package`, `#:property` directives).
- `run.ps1` copies the scenario into `<tfm>/work/` and runs it from there, so `dotnet` finds that folder's
  `global.json` (which SDK) and `Directory.Packages.props` (which EF Core version) by walking up the tree.
- Scenario files use `#:package Name` **without a version**. Versions come from central package management.
  Never put a version in a scenario file, or the .NET 10 and .NET 11 runs stop being comparable.
- `old` = the previous way: must compile and run on **both** SDKs.
  `new` = the new feature: expected to fail to compile (or behave differently) on .NET 10.
  A few EF scenarios are the same code on both SDKs and have only a `new` file (the SQL is what differs).

Commands (PowerShell 7 recommended):

```powershell
./run.ps1 -List
./run.ps1 01-union                      # new variant, both SDKs, sequentially
./run.ps1 01-union -Variant old
./run.ps1 09 -Target net10              # left terminal
./run.ps1 09 -Target net11              # right terminal
./warmup.ps1
./run.ps1 -Clean
```

## Conventions

- Keep each scenario **short** (aim for under ~50 lines of visible code) and readable on a projector.
  Put `LIVE:` comments where the presenter should make a live edit.
- One concept per scenario. Do not add features "while you are there".
- ASCII only in `*.ps1` (Windows PowerShell 5.1 mis-reads BOM-less UTF-8).
- EF scenarios print the EF Core version first. Keep that line.
- Prefer showing generated SQL (`ToQueryString()`, `GenerateCreateScript()`, `LogTo`) over executing against
  a real database. Vector search (scenario 16) needs SQL Server 2025 (Docker container `xe-sql2025`) and an Ollama embedding model.
- Do not put a `global.json` or `Directory.Packages.props` at the repo root: it would apply to both sides.
- Memory safety needs preview flags and costs stage time. Scenario 15 exists only because it was explicitly requested; do not add more `unsafe` scenarios.

## Definition of done

- Every scenario runs on both SDKs with the behaviour described in its header comment.
- `./warmup.ps1` finishes without hanging, and a second run of any scenario takes a few seconds, not tens.
